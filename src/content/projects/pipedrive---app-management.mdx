<CaseSection title="Two decisions I would defend" subtitle="make every option easy to find" id="decisions">
  <CaseBlock label="decision 1 of 2" data-decision="1" title="Group the options by how they are built" pills={['based on developer feedback']}>
    Developers told us they did not see all the options they had. So schema-based extensions (actions and JSON panels) and iframe-based extensions (custom panels and modals) got their own sections. A developer can start from the technology or from the place in Pipedrive. Either way, they see enough about each option to decide what to build and how.

  <CaseBlock label="research" title="Start from research we already had" pills={['market study', 'HVC buying criteria', 'trial company research']}>
    Integrations were one of the top buying needs for bigger customers, and the most important topic for trial companies. So we knew the developer platform had to get better before I drew anything.
  </CaseBlock>
  <CaseBlock label="flows" title="Flows first, with the PM and engineers">

<CaseSection title="One form for each extension" subtitle="what a developer fills in" id="forms">
  <CaseBlock label="forms" title="Short forms, with the limits under each field">
    Each extension type has its own form: a name, a description, a URL or a JSON file, and the places in Pipedrive where it shows. The limits, like 30 characters for a name, are shown under each field. During testing, we got errors from badly formatted JSON files. So the engineers came up with a check for the uploaded file, which was a great help for developers.
